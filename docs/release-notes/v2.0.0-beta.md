# Indx 2.0 beta

**Self-hosted search server for JSON data — with a dashboard, teams, and an MCP endpoint for AI agents.**

Indx 2.0 is a new server around the Indx search engine (IndxSearchLib 5.0). Upload a JSON array,
mark which fields are searchable, and you have typo-tolerant full-text search over HTTP, a
dashboard for the people who manage the data, and an MCP server your AI agents can query.

This is the first public release of the v2 line. It replaces IndxCloudApi v1; the repository
has been renamed from `IndxCloudApi` to `Indx`.

## What's new in 2.0

v2 is a new server on a new engine. IndxSearchLib went from 4 to 5 underneath it, and the
server itself gained most of what people asked v1 for: changing data without reloading,
rebuilding without downtime, and a dashboard someone other than the developer can use.

### A new search engine underneath

IndxSearchLib 5 is what the server bundles now.

- **BM25F scoring across fields.** Weights per field (`weight`), length normalisation per
  field (`bm25b`), and per-query field boosts (`fieldBoosts`) on the search request. A hit in
  the title and a hit in the body are no longer scored as if they were the same field.
- **Coverage** — how much of the query a document actually covers, returned per hit and
  tunable per query (`enableCoverage`, `coverageDepth`, `coverageSetup`). Word-level matching
  per field (`wordIndexing`) alongside the pattern index.
- **Typo tolerance and affix matching** stay on by default; a single fixed configuration
  replaces the numbered presets of v4. No profile to pick, nothing to misconfigure.
- **Vector and hybrid search**: mark fields embeddable, then `search/vector` for nearest
  neighbours and `search/hybrid` for a blended text + vector score.
- **Declared key field.** A dataset can name the document key it already has; inserts and
  updates are addressed by that key from then on.

### Dynamic data operations

Documents change without reloading the dataset, and the index follows immediately.

- Insert, update, partial update and delete, one document or many, addressed by key.
- **Delete by filter** and **update a field by filter**, in one call.
- All-or-nothing batches: a missing key fails the whole request with a 404 that names it.
- Fields not seen at load time are stored but not indexed; use Replace to adopt new fields.

### Rebuilds without downtime

- **Replace** swaps an entire dataset atomically: the new documents are loaded and indexed on
  a shadow engine while the old one keeps answering, then swapped in. The dashboard shows the
  pipeline as live steps and reports lost field roles or a missing key field.
- **Field configuration changes hot-swap the same way.** Change what is searchable or a
  weight, and the rebuild happens on the side; searches never see a half-built index. While a
  build runs the dataset reports `shadowBuildInProgress` and a second build is refused with
  409 `shadowBusy` rather than queued.

### Memory you control: keep-alive and hibernation

Documents live on disk; only the index is in memory. Each dataset has a keep-alive policy:
**Pinned** (always loaded), **Timed** (evicted after N idle hours, reloaded on the next
request), or **Off** (client-managed). Hibernate a dataset to free its memory now; wake it
when needed. Datasets warm in the background at startup, so a large one does not block the
server from coming up.

### The dashboard

Every team has a page with its datasets; every dataset has a page with what you can do to it.

<!-- SCREENSHOT: /teams/{team} — the dataset cards grid with a few datasets in different states
     (Ready, Hibernated), the breadcrumb, "Manage team" on the right, "New dataset" below. -->

- **Field configuration** with weight sliders and type icons. Nothing is searchable until you say
  so; changes rebuild the index in the background while the old one keeps serving.
- **Search preview** with facets and filters, so you can tune before writing a client.
- **Status** — documents, timings, keep-alive, in one place; the header only shows a state when
  it needs attention (loading, indexing, hibernated, error).
- **Boost rules** with schedules, importable and exportable as JSON. Expired rules are flagged,
  and editors are notified when one expires.
- **Synonyms** (experimental) per dataset, with a copy-onto-another-dataset action.
- **Options**: keep-alive policy, replace the documents atomically with live progress, rename,
  transfer to another team, delete.
- **Upload sanity checks**: an export envelope (one document wrapping the real array) is
  flagged before it becomes a one-document dataset; a dataset in an error state gets a
  recovery panel.

### Teams

Datasets belong to teams, and people belong to teams with a role: Admin, Editor or Viewer.
The breadcrumb switches team or dataset in one click, and "New team…" / "New dataset…" live
in the same menus. The dashboard remembers the team you were in last. Transfer a dataset to
another team you administer; deleting a team deletes its datasets, after typing its name.

<!-- SCREENSHOT: the breadcrumb with the team switcher open, showing two teams and "New team…". -->

### Notifications

In-app and by email: a boost rule expired, an API key is expiring or has expired, a new user
registered or confirmed their email. Per-type preferences per user; email is optional and
defaults to console logging until a provider is configured.

### MCP for AI agents

Every server exposes an MCP endpoint at `/mcp`: search, browse, describe a dataset, read its
synonyms. Point Claude, Cursor or any MCP client at it with an API key and the agent can
answer questions from your data. Pair it with the
[Indx Search skill](https://skills.sh/indxsearch/skill-indx-search/indx-search) and the agent
can also set the dataset up.

### A cleaner HTTP API

- **Team-scoped routes**: `/api/teams/{team}/datasets/{dataset}/…` for everything, plus
  `/api/me/datasets` to list every dataset you can reach.
- **Token-only auth.** API keys are created in the dashboard; there is no password login over
  the API.
- **Errors are RFC 9457 problem documents** with a machine-readable `code`
  (`unknownFilter`, `invalidState` with `retryable` and `Retry-After`, `insufficientRole`,
  `shadowBusy`, …). Switch on the code, not the status.
- **A filter token the server cannot honour is a 400**, never a silently unfiltered search.
  Tokens are durable: they survive cache eviction and restarts.
- Swagger UI at `/swagger`; the OpenAPI spec at `/swagger/v2.0-beta/swagger.json`.

### Security defaults

- The seeded admin gets a generated initial password and must change it on first login.
- Registration mode (open, domain-restricted, closed) and email confirmation are instance settings.
- Email confirmation is enforced on API login; revoked API keys are evicted immediately;
  login tokens are retired on password change.
- Cross-origin requests are denied in Production until you configure CORS.
- The license can be fetched automatically from the Indx License Portal with a token, so a
  fresh deployment needs no license file on disk.
- Rate limiting, with one contract: `429` and `code: rateLimited` with `retryAfterSeconds`.
  Login attempts are limited per address, and API calls can be limited per key.

## Upgrading from v1

v2 is not a drop-in upgrade. The routes, the error format and the binary name changed:

| v1 | v2 |
|---|---|
| `/api/{dataset}/search` and 46 other aliases | `/api/teams/{team}/datasets/{dataset}/search` |
| Plain-text or ad-hoc error bodies | `application/problem+json` with `code` |
| An unresolvable filter searched the whole dataset | 400 `unknownFilter` |
| `IndxCloudApi.dll` | `IndxServer.dll` |
| C# types `Indx.CloudApi.CloudQuery`, `ICloudSearchEngine` | `Indx.Http.QueryProxy`, `IServerSearchEngine` (the old names are removed; a build against them fails with the rename in the message) |

The AI skill ships a
[v1 → v2 migration guide](https://github.com/indxSearch/skill-indx-search/blob/main/references/migration-v4-to-v5.md),
and an agent using the skill can do most of the mechanical work.

## Deploy

- **Self-host**: `dotnet publish` and run `IndxServer.dll` anywhere .NET 10 runs. SQLite by
  default; Azure App Service instructions in the README.
- **Azure Marketplace**: the same server as a managed application, with plan tiers.
